# ADR-0010 — No mapper class yet — direct command construction in controllers

> **Context:** Expands [overview.md §6](../overview.md#6-how-users-interact-with-the-system). Detail in [architecture/module-boundaries.md](../architecture/module-boundaries.md).

**Status:** Accepted for v1.0. Re-evaluate when response assembly grows complex.

---

## Context

Controllers translate HTTP requests into commands and pass them to service layer. The translation in v1.0 is mechanical: pull fields off the request DTO, hand them to the command constructor.

```java
public ResponseEntity<ExpenseResponse> create(@AuthenticationPrincipal UserPrincipal p,
        @Valid @RequestBody CreateExpenseRequest req) {
    Expense expense = expenseService.createExpense(p.userId(),
        new CreateExpenseCommand(
            UUID.fromString(req.idempotencyKey()),
            req.amount(),
            req.merchantName(),
            req.expenseDate(),
            req.categories(),
            req.categoryWeights(),
            req.notes(),
            req.paymentMethod(),
            req.bankAccountId()));
    return ResponseEntity.status(HttpStatus.CREATED).body(toResponse(expense));
}
```

Some codebases extract this into a `RequestMapper` or use MapStruct from the very start. The argument is "separation of concerns" — the controller should not know how to build a command.

## Decision

For v1.0, **construct commands directly in controller methods**. No mapper class, no factory.

A private `toResponse(...)` helper inside each controller handles the domain-to-DTO conversion on the way back.

## Consequences

**Positive.**
- Zero indirection — read a controller method and you see exactly what the service receives.
- Easy to refactor — adding a field is one edit per controller, no parallel mapper signature to maintain.
- No annotation processor, no generated code, no build-time magic.

**Negative.**
- The translation logic is co-located with HTTP handling. If a third caller (e.g. an internal admin tool) needs to build the same command, it would re-implement the mapping. Not a real concern at MVP scale.

## Alternatives considered

- **Dedicated `RequestMapper` class.** Equivalent to direct construction but with an extra class for each direction. Adds indirection without adding capability. Both approaches are equally extensible — adding a new endpoint means adding a new command in both cases.
- **MapStruct annotation processor.** Generates mappers at compile time. Useful when there are many mappings and the boilerplate dominates. Premature at MVP scale: there are ~5 controllers and each maps a small handful of fields.
- **Factory pattern.** A factory implies a runtime decision about which translator to use. Translations here are not dynamic — `CreateExpenseRequest` always maps to `CreateExpenseCommand`. No condition to evaluate, no problem for a factory to solve.

The natural next step when response assembly grows complex (e.g. responses requiring assembly from multiple domain objects) is a mapper class, possibly generated by MapStruct. That is a future decision driven by a real problem, not an upfront architecture choice.
